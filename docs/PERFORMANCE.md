# 批量处理与资源验收

2026-10-13，Apple Silicon、macOS 27.2、Python 3.12.13、Docling 2.138.0。本次比较使用同一台机器和同一组三个小样本：两页原生 PDF、一页扫描 PDF、一张扫描图片。模型已下载，设置 `HF_HUB_OFFLINE=1`；统计包含 Python 启动的墙钟时间与转换进程峰值 RSS，不含 GUI、系统其他程序或下载时间。

| 方式 | 三文件总耗时 | 转换进程峰值 RSS |
| --- | ---: | ---: |
| 0.1，每文件新建进程 / 默认推理参数 | 17.79 秒 | 960.7 MiB |
| 0.2，同批复用 / 2 线程推理 / 有界流水线，结果缓存为空 | 11.69 秒 | 777.9 MiB |
| 0.2，三文件全部命中结果缓存 | 0.064 秒 | 21.8 MiB |

本样本首次处理耗时减少约 34%，峰值内存减少约 19%。两种新版输出的 Markdown 均与旧版逐字节一致。这是小样本观察，不是对任意长文档的速度或内存承诺。扫描页像素、表格和内嵌图片仍会影响单文档的资源峰值。

自动回归另处理了 100 份 HTML（20 种内容），第一批复用 80 份，第二批复用 100 份，第二批没有初始化转换器。1,000 文件的文件夹导入测试覆盖异步扫描、重复加入与修改后重新加入。最新数值及样本 SHA-256 保留在 [performance.json](performance.json)，本机原始记录位于忽略提交的 `.build/batch-*.json`。

## 为什么采用单进程批量处理

多个 Docling 进程会各自加载模型，增加内存及 CPU 争用。当前把并行度留给 Docling 内部流水线，同时限制 PDF 解析器和 CPU 推理线程，文件按队列依次处理。导入、结果预览和导出独立在 Swift utility 任务中运行。每批只创建一次转换器，缓存全部命中时不导入重量级 Docling 模块。

转换结束后释放进程与模型，空闲时不轮询、不保温。本次三文件窗口验收后 GUI 空闲快照为 42.8 MiB、CPU 0.0%，没有存活的 Python worker；该快照不包含 WebKit 系统辅助进程，也不代表所有设备的固定占用。停止或退出时向自己拥有的进程组发送 TERM；两秒宽限后清理未退出的后代，并等待读取任务结束。已回归父进程先退出、后代忽略 TERM 且持有 stdout 的情况。

## 内存和磁盘边界

参数集中在 `Backend/runtime.json`：CPU 推理线程 2、流水线批大小 2、队列 4、预览 512 KiB、界面日志 32 KiB、结果缓存 512 MiB / 14 天。PDF 解析器也使用 2 个线程。这些限制不等于整个应用最多 2 个线程或固定的内存硬上限。

队列只保留文件元信息和结果路径，选中时才读取有限预览。导出每次复制 1 MiB，并检查取消；单文件导出先写临时文件，成功后原子替换目标，取消不损坏已有目标。JSON 只重写至多 64 KiB 的来源头部，其余正文流式原样复制。直接复制到剪贴板按用户明确操作读取完整 Markdown。

当前队列的结果不会被缓存淘汰，所以大批次可能临时超过 512 MiB；清空队列或正常退出后再按容量与最近使用时间清理。解析依赖约 1 GiB、模型约 506 MiB，独立于结果缓存。缓存和预览边界都有真实回归测试。

## 更新策略

只下载当前标准 PDF 流水线需要的排版与表格模型，利用 Hugging Face 现有缓存；下载完成必须实际验证离线初始化，再记录引擎锁和模型 snapshot 身份。模型准备失败或被取消不会写入假就绪状态。

转换保持离线，重新验证已有模型也保持离线。上游版本只在用户点击时查询；新版本不自动安装。依赖锁变更后重新准备并验证模型，转换缓存键同时更新。维护者更新锁文件时应运行 `scripts/test.sh` 与 `scripts/verify-engine.py`，再比较典型文档输出。
